## 2. 积分事件相关（数值验证核心）

### 2.1 放水调控优化（每日 / 次日登录）→ 对应表 `PointsRaceGiftReplace`

**说明**：针对不同积分事件开启时的前 n 次事件，做赠送积分（强制替换）分配。  
**实现**：配表。

**匹配与执行（产品原文逻辑）**：

1. 玩家登录后，若积分事件**已开启或即将开启**；
2. 按 `unique_id`（`group_unique_id`）+ **替换开启时间** + `stageID` 匹配行；
3. 取 **B**（开启后前 n 次窗口 / `WindowSpinCount`）与 **C**（赠送次数 / `GiftCount`）；
4. 在 1..B 中**随机抽取 C 个数字**留存列表；
5. 接下来 B 次事件中，列表标注的 spin 次数，按匹配的**替换组 id** 做替换；
6. **优先级**：非新手期 spin 结果期间，除**卡点强行替换**外，本替换优先级最高；
7. 若窗口未结束时，**替换开启时间 / stage 范围 / rate 范围**任意一条不满足 → **提前结束**本次赠送事件；
8. 原事件类型内需能挂「事件类型 ↔ 上表替换组 id」的匹配。

**表头字段（文档截图表）**：

| 字段 | 含义（对照线上命名） |
|---|---|
| `group_unique_id` | 积分事件 unique_id |
| 开启积分事件后前 n 次进行赠送 (B) | `WindowSpinCount` |
| 赠送次数 (C) | `GiftCount` |
| 替换组 id | `GiftReplaceGroupID` → `SlotReplaceGroup` |
| 替换开启时间 | 如 `0.00-24.00`（评论：用于区分开放第几天；不加时间区分会麻烦） |
| stage 范围 | 如 `[1,4]` |
| rate 范围 | 如 `[0,199]` |

替换组本身走既有 `SlotReplaceWeight`（`slotGroupID` / `SlotReplaceGroupID` / `ResultType` / 万分位概率链）。

> 验证时：奖励关内若出现「必中替换」，先排除本 GiftReplace 再谈压制/放水异常。详见 `points-race-checkpoint.md` §6。

### 2.2 首日卡档进度控制在 50% 以上（新手首关）

**说明**：仅针对**新手首关**积分事件卡点。  
**实现**：配表。

**示意表字段**：

| 字段 | 示例 |
|---|---|
| `group_id` | 2001 |
| `stage` | 4 |
| `rate` | 100 |

**流程图（产品白板，摘要）**：

1. 玩家完成新手并解锁积分事件；开关初值 `开关=0`；
2. 每次 spin → 计算结果；
3. 若 `新手spin开关=1` → 直接输出结果；
4. 若 `开关=0`：
   - 当前结果**不是**积分事件 →（按图）不走本卡档逻辑；
   - **是**积分事件 → 读取 `group_id` / `stage_after` / `rate_after`；
   - 若 `group_id = 表内 id` 且 `stage_after`、`rate_after` **≥ 表内值** → 将开关改为 `1`；
   - 否则保持 `0`。

> **验证含义**：首日新手卡点相关「剧本/开关」在进度跨过表内 stage+rate 门槛前保持特殊态；目标体感是卡档进度不低于约 50%。线上表名若与文档不一致，以配置中心实际表为准，回写本处。

### 2.3 付费水池加点逻辑（二测关键变更）

| 项 | 内容 |
|---|---|
| 问题 | 付费水池在**大部分付费后不会生效** |
| 原逻辑 | 付费后，仅对「本次付费可直接获得的体力」按比例蓄水 |
| 方案 | **所有付费按 id 做新表**统一管理 |

**新表示意列**：

| 付费点位 | 付费金额 | 折算后水池蓄水量 |
|---|---|---|
| 爬塔（示例） | 19.99 | 10 |

- 爬塔等「解锁型付费」本身不给体力，旧逻辑无法蓄水 → 必须读表写入水池；
- **有体力的付费**也配进同一张表，统一管理。

**评论口径（bobby）**：金额列可以不配；也可折算后直接配蓄水值，或配系数——「看后端咋弄方便」。  
验证时：不要再假设「只有直购体力才蓄水」；优先核对是否存在 **pay_id → 蓄水量** 表，以及非体力付费（爬塔等）是否写入水池。

> 与旧公式「纯体力美元价值 × 付费金额对应系数」的关系：二测方案是用**按付费 id 查表蓄水**替代/补齐缺表项。见 `open-assumptions.md` §4 更新说明。

### 2.4 权重拆分：积分 vs 非积分（AmpCoef / DecayCoef）

**问题**：压制态或付费加成 spin 时，除积分外还会影响宝箱/活动道具等；且无法精准只加成「小积分」等。  
**原逻辑**：按分组做权重控制。

**修改方案**：

1. 每个事件组合组后增加**标记参数**；
2. 将原事件类型中积分与其它拆成**四行**：
   - 单积分图标替换
   - 双重积分图标替换
   - 三积分图标替换
   - 其它图标替换  
   并各自配置 **增幅系数 AmpCoef / 衰减系数 DecayCoef**；
3. 公式（产品原文）：
   - 加成态：`(增幅系数 × (自身加成系数 + 1)) × 原有概率`
   - 压制态：`(1 - 衰减系数 × 压制系数) × 原有概率`
4. 另一处表述：**加成系数（如有）× 标记参数（非 0）× 万分位概率**；与积分无关的替换组合 **标记参数 = 0**（不受调控）。

> 与 `slot-base-economy.md` 动态调控公式一致。线上若双/三积分 Amp/Decay 仍为 0/0，属 PRD 已点名、配置未补齐的**已知漏洞**（见 SKILL「已知设计缺口」）。

### 2.5 积分事件引导添加

| 引导 | 触发时机 | 表现 |
|---|---|---|
| 首次收集引导 | 机台首次落定积分事件图标 | spin 轮带停稳后全局压暗，对话 + 图标高光；点对话结束后再播飘飞 |
