## 三类「在线时长」（勿混）

| 名称 | 分母 | 分子 | 回答什么 |
|---|---|---|---|
| **单次会话** | `t_online_time` 条数 | `online_time/60` | 每次玩多久 |
| **活跃日日在线** | 当天有 `t_login` 的人日 | 该人日会话时长之和 | 活跃日一共玩多久（默认日深度） |
| 含未登录记 0 的人均日在线 | 所有人日 | 同上或 0 | 会把流失压矮，默认不用 |

登录次数：活跃日 `count(t_login)`，再对人日求均/P25/P50/P75。  
展示习惯时默认报 **均 + P25/P50/P75**，设计对齐 P50、覆盖到 P75。

## 习惯结论（同队列，重点 D1–D3）

队列 **n=15,851**（US 8175 / GB 7676；安卓 9358 / 苹果 6493）。

| 指标（活跃日） | 均 | P25 | P50 | P75 |
|---|---:|---:|---:|---:|
| 登录次数 | 2.49 | 1 | 1 | 3 |
| 单次会话（分） | 11.54 | 3.18 | 6.54 | 13.46 |
| 日在线（分） | 28.22 | 9.12 | 18.26 | 29.35 |

**产品读法**

1. 典型活跃日是「少登、短局、日累计约一刻钟到半小时」。  
2. 节奏应按「**多次 5–10 分钟**」而不是「一场 30 分钟」。  
3. 差异主轴是**付费深度**，不是地区（US≈GB；苹果略勤/单局略短）。  
4. **推送**：当地 **5–9 点**高峰；**下午避开**；夜 21–23 可作次选。

## 安卓 / iOS 典型画像（同队列，D1–D3）

两端差在**节奏**，不在「一天玩多久」。登录当地钟点同形；付费时机更稳的口径是**相对注册多久 + 卡在积分阶段 4**（尚未按端拆「付费当地小时」）。

| | 安卓（n=9,358） | iOS / 苹果（n=6,493） |
|---|---|---|
| 节奏标签 | 少登一点、单局略长 | 更勤、单局更碎 |
| 活跃日登录（D1–D3） | P25/50/75 = **1 / 1 / 2**（均 2.40） | **1 / 2 / 3**（均 2.90） |
| 单次会话 P50 | **~7.1 分** | **~6.0 分** |
| 日在线 P25/50/75 | **9.3 / 18.6 / 29.0** | **8.9 / 17.9 / 30.3** |
| 当地登录 | **5–9** 主峰（约 9 点最高），13–18 谷，**21–23** 次峰 | **同形**，无端专属深夜党 |
| 付费时机 | 多在 **D1**，开局后很快（常见半小时～1 小时内破冰；流失侧更「快付」） | 同结构；破冰仍多卡在积分阶段 4 |
| D1 付费→D2 回访 | **~51.6%** | **~65.2%** |

**安卓读法**：偏「打开一次多玩一会儿」；日总量仍不到半小时。  
**iOS 读法**：偏「一天多点几次、每次更短」；叠起来的日深度与安卓接近。

**运营含义**：两端都按多次 5–10 分钟设计；推送不必分端做两套钟点；评估买量时单独看「D1 付费次日留存」时注意 **US/安卓更弱**（相关，非已证因果）。明细 → `references/2026-09-14-findings.md` §0.1。

## 「快付 + 浅玩」数据表征（固定定义）

仅对 **D1 有 `t_pay_flow` 且 cost>0** 的用户打标：

```text
快付  = date_diff('minute', reg_time, first_pay_time) < 30
浅玩  = D1 活跃日总在线分钟 < 60
      （分母：当天有登录；分子：sum(t_online_time.online_time)/60）
快付浅玩 = 快付 AND 浅玩
```

已测规模（习惯主队列 8/25～9/02）：快付浅玩 **125** 人；D2 回访率 **32.8%** vs 其他 D1 付费 **66.2%**。  
在 D2 流失的 201 人里，快付浅玩占 **41.8%**；在 D2 回访 270 人里仅 **15.2%**。

## 画像 1.1 × A/B/C × 双端（2026-09-14）

报告「1.1」= 首日付费 ∧ 次日未登 ∧ 快付浅玩 ∧ 终停阶段 6 ∧ area≤103。  
扩窗注册 **8/25～9/12**（与习惯主表至 9/02 不同；D1 付费 **643**）。明细 → `references/2026-09-14-persona11-abc.md`。

| 切点（会话 UTC-4） | 含义 |
|---|---|
| A：`reg < 08-31 10:29:48` | 改前（北京 08-31 22:29:48；注册 ≥08-25） |
| B：至 `reg < 09-02 22:37:10` | 解锁+卡点逻辑修改期 |
| C：之后 | 北京 09-03 10:37:10 回退后 |

**实测**：画像 **69** 人 = 占 D1 付费 **10.7%** = 占 D2 流失 **24.8%**。  
A/B/C 占 D1 付费 **10.8 / 10.9 / 10.5%**（几乎无差）。Android **12.2%** vs iOS **8.7%**；流失内部两端皆 ~25%。

**读法（勿判成买量突变）**

1. 稳定**体验型**流失包，不是 A/B/C 人群结构冲大。  
2. 调卡点/解锁**没削掉**这批人的浓度；B 次留变好更像其他付费人受益。  
3. Android 更糟主因是**流失面更大**，不是流失结构更偏此画像。  
4. 只解释「付费次日不回」的一块，**≠** 大盘次留/三留下滑因果。  
5. 产品刀打「快付后过第二卡点 / 浅玩目标 / 更深地图」，不要先怪某一期买量。

## D1 付费 → D2 回访分析骨架

1. 圈 D1 付费用户 + `has_d2`（D2 是否有 `t_login`）  
2. 对比：金额、首付速度、D1 登录/日在线/`t_slot` spin、`t_point_race` 最高阶段、`t_build` 最高 `area_id`  
3. 付费后：是否 power→0、付费→当日最后事件分钟数、付费后 `t_point_race` 条数  
4. 交叉：快付×浅玩四分位  

### 已排除 / 已确认（勿重复踩坑）

| 假设 | 结论 |
|---|---|
| 付费后立即体力耗尽导致流失 | **否**。回访者更常打到 power=0 |
| 只有流失卡在积分阶段 4 | **否**。两边首付时阶段 P50 都是 **4** |
| 付费多少决定 D2 回访 | **否**。金额 P50 接近 |
| 快付浅玩 / 付费后很快离开 | **强相关** |
| 地图到达 area≥104 | **强产品假设**（回访 48% vs 流失 32%） |
| 任意事件 `curr_power=0` | **不可用**；只可谨慎看 login/logout |
| 地图 `polt_id` | **不可用**；用 `area_id` |
