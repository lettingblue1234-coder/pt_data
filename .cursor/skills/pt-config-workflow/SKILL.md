# PT 需求 → 配置落地工作流

项目：**Piggy Tycoon**（PT，数数 project_id **261**）。

## 信息源与权威顺序

| 要什么 | 去哪拿 | 备注 |
|---|---|---|
| 当前版本焦点、入口、规范 | **飞书【首页】** | **任何配置工作开始前先浏览首页** |
| 排期 / 版本节点 / 提测封版时间 | **飞书知识库**（排期页） | 涉及上线时间就拉，别凭印象 |
| 线上配置（真值） | **pango-MCP** | 环境：**测试服 / 体验服 / 预发布服**，以及 **SVN** 配置源 |
| 客户端逻辑、UI、弹窗、埋点 | **本地客户端代码**（已拉取） | 先 grep 表名 / 字段名 / scene_id |
| 服务端逻辑（发奖、触发、限购、过期） | 飞书问 **PT开发小助手** | 代码不在本地；问到的结论要写回 references |
| 线上数据 | **AE（数数）MCP** 或 `ae-cli` | 口径见 `piggytycoon-sql` / `pt-ae-sql`；登录见 `ae-cli-auth` |
| 已沉淀的枚举 / 结论 | 本仓库 skills | `piggytycoon-sql/references/enums.md` 是 scene / trade / page 速查 |

冲突时：**pango 线上配置 > SVN > 客户端代码 > 飞书文档 > 本仓库沉淀**。发现沉淀过期就改沉淀。

## 开工前先探测工具

MCP 名称会变，先查再调，**不要猜工具名**：

1. `GetDynamicTools` 用 pattern `(?i)pango|feishu|lark|飞书|ae|thinking|shushu` 查命名空间。
2. 对命中的命名空间再拉完整 schema 后调用。
3. 状态是 `needsAuth` 的先走 `mcp_auth`；AE 走 `ae-cli-auth` 的 split-flow。
4. **拿不到的源要明说**（例如云端环境里没有 pango / 飞书），在方案里标「待拉取」，**不要编配置值**。

## 标准流程

1. **读首页**：飞书【首页】→ 记下当前版本号、在做的需求、配置规范链接。
2. **查排期**：知识库排期页 → 本需求能进哪个版本、提测/封版日、四个环境的推进节奏。
3. **拉现状配置**（pango，按 测试服 → 体验服 → 预发布服 → SVN 逐个比对）：
   - 本需求涉及的表全量行 + 相关联表（商品表、触发条件、弹窗优先级、奖励表）。
   - 记录环境间差异：**同一张表各环境不一致是常态**，方案以「要上的那个环境」为基线。
4. **对照客户端代码**：入口、弹窗队列、倒计时、红点、埋点 `scene_id/page_id` 是否已支持。
5. **问 PT开发小助手**（服务端）：用 `references/dev-assistant-questions.md` 的模板，一次问清。
6. **拉数据基线**（AE）：需求影响的指标在改动前的值 → 作为验收对照。
7. **出方案**：配置 diff（表 / 行 / 字段 / 旧值 → 新值 / 环境）+ 风险 + 验收口径。
8. **写回沉淀**：确认的表名、字段含义、服务端规则写进本 skill `references/`，commit。

## 输出格式

- 开头一句话结论（改什么、在哪个环境、哪天能上）。
- 配置 diff 表：`环境 | 表 | 主键 | 字段 | 现值 | 新值 | 理由`。现值未拉到写「待拉取」。
- 依赖与冲突：同期弹窗/礼包、新手期剧本、积分卡点。
- 验收：指标、口径、对照组、样本阈值（分子 ≥30 可用）。
- 未决问题清单（谁来答：策划 / 开发小助手 / 数据）。

## 纪律

- **只读**：pango 默认只读，写配置必须用户明确授权，且只写测试服。
- **按 ID 聚合**：`trade_id` 中文名不唯一（如 `6005004/5/6` 都叫「三段礼包」）。
- **埋点一起上**：新礼包没有独立 `scene_id` / `page_id` 就没法验收，方案里必须写。
- 数据口径、时区、观测期规则全部沿用 `piggytycoon-sql`，不在本 skill 重定义。
