### 时区与日界　★ 本轮最容易出错的地方

查询页面右上角的时区选择器是 **UTC-4（西四）**，看板底层也是西四。这个设置对本轮是合适的：

- 美东 8 月是 EDT，正好等于西四，**看板的一天就是美东玩家的自然一天**
- 英国是 BST（东一），西四日界落在英国凌晨 5 点，低活跃时段
- 反过来若按东八切，日界落在美东中午、英国下午 5 点——会把同一个玩家的上午场和晚上场分到两天

**所以不要切回东八。** 留在 UTC-4，分区、事件时间、看板三者才对得上。

### 口径：两套并行，分别取数

| 口径 | 定义 | 切法 | 适合 |
|---|---|---|---|
| **A · 西四自然天** | 按西四的自然日切 | `date("#event_time")` | 大盘日报、DAU、对齐看板 |
| **B · 24 小时自然桶** | 按每个人的注册时刻起算 | `date_diff` 折算小时数分桶 | 留存、LTV、首付时机——人和人可比 |

```sql
-- 口径 A：西四自然天（不要用 $part_date 当维度，它的时区未验证）
date("#event_time") AS stat_date

-- 口径 B：24 小时自然桶（0-24h / 24-48h / 48-72h）
CAST(date_diff('second', u.register_time, e."#event_time") / 3600.0 AS DECIMAL(10,2)) AS hours_since_reg,
CAST(date_diff('second', u.register_time, e."#event_time") / 86400 AS bigint)          AS day_bucket
```

**两套口径的数对不上是正常的**，尤其是 D0：口径 A 的 8/25 只有 9 小时，口径 B 的 D0 是完整 24 小时。出报告时必须标明用的哪一套，不要混着引用。

跨日窗口查询时 **`$part_date` 上界要放宽一天**——北京时间 23:57 注册的人，24 小时窗口会跨到次日分区。口径 B 尤其要注意，否则最后一天的桶会被截断。

### 取数前先确认　★

**每次动手写 SQL 之前，先问清楚这次要哪个口径**，不要默认、不要自己挑一个先跑。要确认的是：

1. 这次用口径 A、口径 B，还是两套都出？
2. 时间范围到哪天截止（口径 B 需要观测期够长，最后一批人的桶可能不完整）？
3. 是否需要拆操作系统 / 拆地区？

口径没定就开跑，是上一轮返工最多的原因——同一个「付费率」因为切法不同出过三个数，谁都说不清哪个对。

## 一、通用规则

| # | 规则 | 说明 |
|---|---|---|
| 1 | **引擎是 Trino / Presto，不是 ClickHouse** | 反引号报 `backquoted identifiers are not supported`。字段名用双引号；用 `date()` / `date_diff()` / `COUNT(DISTINCT)` / `UNNEST(ARRAY[...])` 这类标准写法 |
| 2 | **所有埋点在一张宽表 `v_event_261`** | `"$part_event"` 区分事件类型，`"$part_date"` 按天分区 |
| 3 | **必带 `"$part_date"` 过滤** | 分区表硬性要求。本轮下限用 `'2026-08-18'`（往前放宽，涵盖内部测试期）。只做裁剪，**不要拿它当统计维度** |
| 4 | **不写行尾注释** | `FROM user -- 注释` 会报错。注释独占一行，或干脆不写。实践上全英文别名、零注释 |
| 5 | **一次一条，拆成 N 个独立文件** | 不要把多条查询塞一个文件里跑 |
| 5b | **写 SQL 前先确认时间口径** | 东八自然天 / 24 小时桶 / 两套都要，先问清楚再动手。详见 §0 |
| 6 | **首字符检查** | 部分工具会吃掉首字母，确认是 `SELECT` 不是 `ELECT` |
| 7 | **主查询零 JOIN，人群用 `IN` 半连接** | JOIN `t_register` 会因重复注册记录放大行数（上轮有 9 个账号 `reg_event_cnt = 2`）。JOIN `ta.v_user_261` 是安全的，它一账号一行 |
| 8 | **不要用服务端算好的派生字段** | `total_pay_cnt` 曾算在放大后的数据上，把 4 笔记成 8 笔。序号 / 总数 / 是否首次一律拿回本地算。**`ftime` 属于此类，首次使用前先验证**（见 3.1） |
| 9 | **先跑字段探查，再取明细** | 上轮 `point_change_cnt` 全空、`t_slot.power_*` 全为 0、`trigger_time` 写死，都是探查发现的 |
| 10 | **金额先整数分聚合，最后转定点；比率一律加 `nullif`** | 见 §5 |

## 二、表结构

### 2.1 事件表 `v_event_261`

所有埋点共用的宽表，**不是一个事件一张表**。

- `"$part_event"`：事件类型，如 `t_register`、`t_pay_flow`、`t_user_track`
- `"$part_date"`：按天分区（北京时间），查询必带
- `SELECT *` 会把其他事件的字段一起带出来（对当前事件无意义、全 NULL），取数时显式列字段

### 2.2 用户属性表 `ta.v_user_261`

一账号一行的**当前最新属性快照**（等级、金币、累计付费等），和事件流水是两回事。需要 `register_time` 算时间窗口时从这里取。

同库里的 `user_result_cluster_261`（标签分群）、`user_day_serial_261`（每日镜像）不是这个用途。

### 2.3 显示名 ≠ 真实物理字段名

后台属性列表页的 **`ta_name` 列才是真实字段名**。已知的坑：

| 显示名 | 真实字段 | 备注 |
|---|---|---|
| `country` | `#country` | 直接写 `country` 报 `Column cannot be resolved` |
| `fn_uid`（发行账号ID） | `#account_id` | 不是独立字段，别重复选 |
| — | **`t_pay_flow` 下没有 `#country_code`** | 只有 `#country` |
| `plot_id` | **`polt_id`** | 拼写就是错的，照抄 |

**遇到「字段不存在」，先查 `ta_name`，不要猜。**

### 2.4 数值型 ID 是 double

`user_action` / `trade_id` / `scene_id` / `page_id` 都是 double。

- 比较时**不加引号**：`user_action = 1` 而不是 `user_action = '1'`
- 要和字符串 `coalesce`：`CAST(CAST(x AS bigint) AS varchar)`

## 三、pay_flow 字段更新

### 3.1 `ftime`：含义存疑，暂不使用　⚠️

基建文档写它是「首次付费时间」，但 `t_default` 公共属性列表里 `ftime` 的释义是 **「时间(毫秒)」、整型、所有事件都带**，配套还有一个 `fday`「日期」——看着是通用的事件时间戳，不是首付时间。

**在验证清楚之前不要用它判首单。** 目前首充查询用 `row_number() OVER (PARTITION BY aid ORDER BY event_time)` 自己算。

验证方法：取几个付费玩家，看 `ftime` 转成时间后是否等于该笔的 `#event_time`。相等则是普通时间戳。

### 3.2 `trade_id`：枚举与实测存在矛盾　⚠️

**TRADE_TYPE 枚举表显示每张通行证有独立 ID**：

| trade_id | 名称 |
|---|---|
| 3001001 | 建造通行证 |
| 3001002 | 日常任务通行证 |
| 3001003 | 机台升级通行证 |
| 3001004 | 甜蜜循环通行证 |
| 3001005 | 高级通行证 |

但**上一轮的实测记录是「四张 Pass 共用 3001002 / 3001003」**。两者矛盾，可能是版本变更，也可能是上一轮数据确实那样记。

**在数据验证之前，仍然按 `(scene_id, trade_id)` 组合取数**，不要只用其中一个。验证方式：看同一个 `scene_id` 下是否出现多个 `trade_id`。

另注：`trade_id` 的中文名**不唯一**——`6005004/5/6` 都叫「三段礼包」，`6001001~4` 都叫「三选一礼包」，`8008002` 与 `6008002` 都叫「体力转盘899」。**聚合必须按 ID，不能按名字**，否则会把不同档位合并掉。

### 3.3 `packagekey`：待确认

计划新增，用于区分**相同价格、相同场景下不同付费内容**的礼包。这个字段落地之前，「同场景同价格的不同礼包」在数据上仍然是混在一起的，相关分析先不要下结论。

## 四、user_track 曝光表枚举　★ 本次核心更新

`t_user_track` 记录玩家点击轨迹。四个关键字段：`page_id`、`scene_id`、`user_action`、`trigger_time`。

### 4.1 `user_action`：行为类型

| 值 | 含义 | 说明 |
|---|---|---|
| 2 | **曝光** | 主要是弹窗自动弹出 |
| 1 | **点击** | 玩家主动点击 |
| 0 | 默认 | 未归类 |

> ⚠️ **纠正上一版**：曾把 `user_action = 1` 当成「入口曝光」，导致 6 条曝光相关结论被撤回。**1 是点击，2 才是曝光。**

### 4.2 `trigger_time`（触发方式）

| 值 | 含义 |
|---|---|
| 101 | 玩家主动点击 |
| 0 | 默认（自动曝光弹出） |

上轮该字段 27.4 万条里唯一值只有 101，当时误判为「写死的废字段」剔除掉了。本轮有了枚举，**它是区分主动 / 系统触发的关键，不要剔除**。

### 4.5 漏斗口径模板

有了枚举，标准曝光漏斗可以这么写（以礼包大类为例）：

```sql
SELECT
    scene_id,
    count(DISTINCT CASE WHEN page_id = 26 AND user_action = 2 THEN "#account_id" END) AS entry_exposed,
    count(DISTINCT CASE WHEN page_id = 26 AND user_action = 1 THEN "#account_id" END) AS entry_clicked,
    count(DISTINCT CASE WHEN page_id = 27 AND user_action = 2 THEN "#account_id" END) AS panel_exposed,
    count(DISTINCT CASE WHEN page_id = 28 AND user_action = 1 THEN "#account_id" END) AS closed
FROM v_event_261
WHERE "$part_event" = 't_user_track'
  AND "$part_date" >= '2026-08-25'
GROUP BY scene_id
```

三个提醒：

- 入口一般是**曝光**（`user_action = 2`），点击必须玩家触发；界面既可能是弹窗曝光、也可能是主动点开，**同一个 page_id 的 1 和 2 要分开统计**，不要合并
- 通行证把 26/27/28 换成 57/58/60，`59`（收集奖励）是玩法行为不是购买漏斗的一环
- 曝光只覆盖部分收入。上轮 `t_user_track` 只对上了 52.6% 的付费收入，**不要用曝光侧人数当付费漏斗的分母**

## 五、人群模板与精度规范

### 5.1 人群模板（本轮）

```sql
-- 方式一：IN 半连接（主查询不需要 register_time 时）
AND "#account_id" IN (
      SELECT "#account_id" FROM ta.v_user_261
      WHERE lower(country) IN ('us','gb')
        AND register_time >= TIMESTAMP '2026-08-25 15:00:00'
    )

-- 方式二：CTE + JOIN（需要 register_time 算窗口时）
WITH cohort AS (
    SELECT "#account_id" AS aid, register_time
    FROM ta.v_user_261
    WHERE lower(country) IN ('us','gb')
      AND register_time >= TIMESTAMP '2026-08-25 15:00:00'
)
```

**本轮必须加操作系统维度。** 安卓和 iOS 的付费能力、留存、包体加载都不同，合在一起看会互相稀释。建议所有汇总类查询默认 `GROUP BY os`，而不是事后再拆。

**操作系统字段已确认**：在 `t_default` 公共属性里，字段名是 `os`（**无 `#` 前缀**，`#os` 会报 cannot be resolved）。取值只有两个：

| 原始值 | 归一化 |
|---|---|
| `IPhonePlayer` | ios |
| `Android` | android |

`IPhonePlayer` 是 Unity 的运行时字符串。归一化写显式 CASE、其余落 `other`，**不要写 `ELSE 'ios'`**——否则 `WindowsEditor` / `OSXPlayer` 这类内部测试机会被静默算进 iOS。

同一张表里的 `platform` 字段虽然是必填，但取值全是 `piggytycoon_global`（发行包标识），**不能用来分操作系统**。

### 5.2 精度规范

根因：CTE 里写 `cost / 100.0 AS usd` 先转浮点、再 `sum()`，误差累积。`49.910000000000004` 就是 `9.98 + 39.93` 在二进制浮点下的结果。

```sql
-- ✗ 先除后加
sum(cost / 100.0) AS revenue
-- ✓ 整数相加 + 定点输出
CAST(sum(cost) / 100.0 AS DECIMAL(12,2)) AS revenue
```

| 类型 | 写法 | 精度 |
|---|---|---|
| 金额、收入 | `CAST(sum(cost) / 100.0 AS DECIMAL(12,2))` | 2 位 |
| 客单、人均付费 | `CAST(sum(cost) / 100.0 / nullif(n,0) AS DECIMAL(10,2))` | 2 位 |
| **ARPU** | `CAST(sum(cost) / 100.0 / nullif(n,0) AS DECIMAL(10,4))` | **4 位** |
| 比率、百分比 | `CAST(a * 100.0 / nullif(b,0) AS DECIMAL(6,2))` | 2 位 |
| 倍数、均值 | `CAST(a * 1.0 / nullif(b,0) AS DECIMAL(8,2))` | 2 位 |
| 小时数 | `CAST(date_diff('second',a,b) / 3600.0 AS DECIMAL(10,2))` | 2 位 |
| 计数 | 保持 `bigint` | — |

配套：CTE 里金额保持整数分；分层阈值也用分（`total_cent < 200` 而非 `total_usd < 2`），整数比较无边界误差。
