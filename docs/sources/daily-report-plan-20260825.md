## 二、两块视角

日报分两块，口径本质不同，**不能互相印证**。

| | 块 1 · 新增玩家（q1–q3） | 块 2 · 全量大盘（q4） |
|---|---|---|
| 视角 | 按注册日切队列 | 按自然日切 |
| 时间轴 | 距注册的 24 小时桶 | 西四自然日 |
| 一行代表 | 某天注册的一批人，在他们自己的第 N 天 | 某一天全服发生了什么 |
| 人群 | 只有当批新增 | 新 + 老 |

**两块的付费率一定对不上**，因为分母不同：块 1 是「某批新增在他们的次日有多少付费」，块 2 是「某天全服活跃里有多少付费」。都对，但表头必须写清口径，否则每周都要解释一次。

## 三、口径决策记录

### 时区

- 查询页面时区选择器设为 **UTC-4（西四）**，看板底层也是西四，**不要切回东八**
- 西四对本轮是合适的：美东 8 月的 EDT 正好等于西四，看板的一天就是美东玩家的自然一天；英国那边日界落在凌晨 5 点，低活跃时段
- 若按东八切，日界会落在美东中午、英国下午 5 点，把同一个玩家的上午场和晚上场分到两天
- 自然日维度用 `date("#event_time")`，**不用 `$part_date`**（它的时区还没验证过，只拿来做分区裁剪）

### 测试起点

- 基建文档：**北京 2026-08-24 15:00 = 西四 08-24 03:00**
- 曾一度记成 8/25 15:00，数据侧证伪：看板显示 8/24 注册 594 人、8/25 仅 75 人
- **cohort 起点统一放宽到 8/18**，每个注册日自己成行——开量日是哪天，让数据自己显示，不靠拍板

### 留存与日桶命名

确认的映射是 **第 N 日 = D(N-1)**：

| 叫法 | 日桶 | 距注册 |
|---|---|---|
| 次日留存 | D1 | 24–48h |
| 三日留存 | D2 | 48–72h |
| 四日留存 | D3 | 72–96h |
| 五日留存 | D4 | 96–120h |
| 七日留存 | **D6** | 144–168h |
| 14 日留存 | **D13** | 312–336h |

⚠️ 留存表的「七日」是 D6，但 LTV 表的 LTV7 是 D7，**两个 7 不是同一天**。两张表并排放时容易读串。

首批只出 D1–D4，D6 / D13 等观测期够了再补（改 `buckets` 里的 `ARRAY` 即可）。

### 分母

| 指标 | 分母 |
|---|---|
| 留存率 | 观测期已满的人数 |
| 付费率（块 1、块 2） | 当日活跃 |
| ARPU | 当日活跃 |
| ARPPU | 当日付费人数 |
| LTV | 注册人数 |
| 累计 ARPU（块 2） | 当日 DAU |

⚠️ **累计 ARPU 会随时间单调上升**——分子累计、分母不累计。它读起来像「当前每个活跃用户身上已产生的历史收入」，趋势天然向上，不代表变现效率提升；DAU 掉的时候它还会跳升。所以表里和「当日 ARPU」并排放，两条线一起看。

### 观测期未满

**每个 Dn 只统计注册满 n+1 天的人**，分母随 n 收缩。

加了注册日维度之后这个问题基本消解：同一天注册的人观测期一致，所以每行内部分母恒定，某个日桶要么整行有数、要么整行为空。**老板横着看一行就是同一批人的曲线，不会踩坑。**

表里保留 `观测人数` / `注册人数` 列，并用 `WHERE > 0` 过滤掉全空行。

### 拆分粒度

三张队列表都拆四段（地区 × 系统）+ 注册日；大盘表用 `GROUPING SETS` 同时出总量和四段。

**依据：决定精度的是分子，不是分母。** 二项分布的相对标准误约等于 `1/√分子事件数`：

| 指标 | 分段人数 | 分子 | 相对标准误 | 95% 区间 |
|---|---|---|---|---|
| D1 留存（p≈35%） | 45 | ≈16 人 | 约 20% | 21% – 49% |
| 付费率（p≈2.9%） | 45 | ≈1.3 人 | 约 86% | 0% – 7.8% |

同样 45 人，留存能看方向，付费率的区间包含 0 且跨度是点估计的 2.7 倍，等于没信息。金额类更糟：ARPPU 是重尾分布的均值，只有 1 个付费者时它就是那个人的账单。

因此每张表都带 **`样本提示`** 列自动标记：

| 分子 | 标记 |
|---|---|
| ≥ 30 | 可用 |
| 10–29 | 仅看方向 |
| < 10 | 样本不足 |

按当前量级预估，留存表大多是「仅看方向」，付费和 LTV 表几乎全是「样本不足」——这个结果本身就是信息。

### 呈现

- 表头和维度值全中文：`美国` / `英国`、`苹果` / `安卓`、`8月25日注册`
- 排序走隐藏的日期列和桶序号，不按中文字典序（否则「8月9日」会排到「8月25日」前面）
- `ARPU$` / `ARPPU$` / `LTV$` 保留英文缩写，和现有看板一致

## 四、字段与枚举

### 操作系统

字段是 `t_default` 公共属性里的 **`os`（无 `#` 前缀）**，`#os` 会报 cannot be resolved。

| 原始值 | 归一化 | 8/25 时点人数 |
|---|---|---|
| `IPhonePlayer` | 苹果 | 511 |
| `Android` | 安卓 | 90 |

`IPhonePlayer` 是 Unity 的运行时字符串。归一化写显式 CASE、其余落 `其他`，**不要写 `ELSE '苹果'`**——否则 `WindowsEditor` / `OSXPlayer` 这类内部测试机会被静默算进 iOS。

同表的 `platform` 虽是必填，但取值全是 `piggytycoon_global`（发行包标识），**不能用来分系统**。

### 重复注册

`t_register` 里 iPhone 是 512 行对 511 人——仍有账号存在两条注册记录。**取 os 必须先 `max(os) GROUP BY aid` 聚合成一账号一行再 JOIN**，否则人数放大。

### 枚举表

三张 CSV 已内联进 `_enum_maps_snippet.sql`：SCENE_TYPE 45 条、TRADE_TYPE 83 条、PAGE_TYPE 110 条。

用 `LEFT JOIN` 挂接、匹配不上的显示成 `未知场景_xxx`，**不要用写死的 CASE**——这样枚举有缺口时能立刻看见。

对照基建更新发现的差异：

| # | 发现 |
|---|---|
| 1 | **`trade_id` 能区分通行证玩法**：3001001 建造 / 3001002 日常任务 / 3001003 机台升级 / 3001004 甜蜜循环 / 3001005 高级。与上一轮「四张 Pass 共用 3001002/3001003」的记录矛盾，需用数据验证 |
| 2 | `scene_id` 清单漏了三个：`5` 甜蜜循环普通区代币礼包、`6` 甜蜜循环高级区代币礼包、`10` 日常任务代币礼包 |
| 3 | 礼包 page 段不止 26–28，还有 **29–34**（二次确认框、一键购买、档位购买、未解锁提示） |
| 4 | 通行证 page 段不止 57–60，还有 **35–40**（购买选择界面、普通/高级购买按钮、说明气泡、保险箱） |
| 5 | PAGE_TYPE 有 **22 条标着「0.6.0 弃用」**，含 72/73/74（三段礼包旧入口）。若本轮这些 ID 仍有数据，说明客户端版本或埋点没跟上——是个现成的校验点 |
| 6 | `page_id = 42` 是「商城购买按钮-首充状态」，专门标记首充 |
| 7 | **`trade_id` 中文名不唯一**：6005004/5/6 都叫「三段礼包」，6001001~4 都叫「三选一礼包」，8008002 与 6008002 都叫「体力转盘899」。**聚合必须按 ID，不能按名字** |

### 行为埋点语义（上一轮曾搞反）

| 字段 | 值 | 含义 |
|---|---|---|
| `user_action` | 2 | 曝光（多为弹窗） |
| | 1 | 点击（玩家主动） |
| | 0 | 默认 |
| `trigger_time` | 101 | 玩家主动点击 |
| | 0 | 自动曝光弹出 |

上一轮把 `user_action = 1` 当成入口曝光，导致 6 条结论被撤回。**1 是点击，2 才是曝光。**

`page_id` 是场景内局部编号、跨场景重号，查询时必须 `(scene_id, page_id, user_action)` 三个一起限定。

1. **每次跑 q1/q2/q3 前**，把三个文件里的 `TIMESTAMP '2026-09-01 00:00:00'` 改成实际拉数时刻。不改的话观测期判断是错的

4. 枚举更新时只改 `_enum_maps_snippet.sql` 那两段，其余不动

## 六、待确认

1. **场景要按「付费活动」和「活跃活动」分类**——SCENE_TYPE 共 45 条，其中约 17 条与礼包/通行证付费相关，其余是好友、公会、签到、锦标赛、新手引导等活跃向场景。做付费分析时不该把活跃活动的场景算进来。

   这个分类**需要业务侧给，不自行判断**：从名字上猜不出来——「体力转盘活动」听着像活跃场景，但 TRADE_TYPE 里有 `8008001~8008007` 七个付费档；反过来「新手引导」`10019` 上一轮在 `t_user_track` 里是 0 条。分类给了之后，q5 和后续付费分析加一层场景过滤即可
2. **测试起点最终确认**：基建文档写 8/24 15:00，口头一度说 8/25 15:00
3. **`$part_date` 的时区**——诊断查询（`part_date` vs `date("#event_time")` 分组计数）在 8/25 当天跑过一次只出 1 行，但那时数据还没跨过任何日界，证明不了什么。现在已跨过，可以重跑
4. **`register_time` 与 `#event_time` 是否同时区**——属性表和事件流水两条链路，若不一致，24 小时桶会整体偏移
5. **`ftime` 的含义**：基建文档写「首次付费时间」，但 `t_default` 公共属性里它的释义是「时间(毫秒)」、整型、所有事件都带，看着是事件时间戳。q5 没用它，用 `row_number()` 自己算的
6. **`country` 可能有两个**：`t_default` 里有自定义的 `country`（无前缀），预置属性是 `#country`，取值未必一致
7. **`packagekey` 是否落地**——没有它，同价格同场景下的不同礼包内容在数据上分不开，q5 那张表届时要重做
8. 首充表跑出来后核对：同一场景下是否出现多个 `trade_id`（验证第四节第 1 条），以及有没有「未知场景 / 未知商品」的行
