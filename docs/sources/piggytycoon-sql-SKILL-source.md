# PiggyTycoon 数据分析

这个 skill 装的是**已经用错误换来的知识**：字段名、口径决策、被推翻的结论、以及一套自检清单。目的是不重犯同样的错。

## 开工前必做

写任何 SQL 之前，先确认三件事。这三件事每一件搞错都**不会报错**，只会静默给出错误的数：

1. **会话时区**——查询页右上角的选择器。决定所有时间字面量怎么写
2. **观测期截止时刻**——就是"现在拉数的时间"。多个查询里有写死的 `TIMESTAMP`
3. **本次要用的队列范围**——iOS 的付费数据从 8/28 才有效（之前走沙盒渠道）

如果用户没说，就问。不要默认。

时区判断可以用这条：

```sql
SELECT min("#event_time") AS first_event
FROM ta.v_event_261
WHERE "$part_event" = 't_register' AND "$part_date" = '2026-08-24'
```

测试从北京 8/24 15:00 开始。显示 15:00 左右 = 东八，03:00 左右 = 西四，07:00 左右 = UTC。

## 环境事实

| 事实 | 说明 |
|---|---|
| 引擎 **Trino/Presto** | 反引号报错。字段名用双引号 |
| **不支持行尾注释** | 注释独占一行，实践上全不写 |
| 所有埋点在 **`ta.v_event_261`** | `"$part_event"` 区分事件，`"$part_date"` 按天分区 |
| 用户属性表 **`ta.v_user_261`** | 一账号一行，JOIN 安全 |
| 工具会**吃首字母** | 粘贴后确认第一个词是 `WITH` 不是 `ITH` |
| `$part_date` 与 `date("#event_time")` 一致 | 已验证，跟随会话时区 |

## 字段（全部实测过）

| 要什么 | 写什么 | 坑 |
|---|---|---|
| 国家 | 事件表 **`"#country"`**；用户表 `country` | 事件表写 `country` 报 cannot be resolved |
| 操作系统 | **`os`**（无 `#`） | `#os` 报错。值只有 `IPhonePlayer` / `Android` |
| 平台 | `platform` **不可用** | 全是 `piggytycoon_global`，是发行包标识 |
| 商品 | **`trade_id`** | **`product_id` 全是 NULL**，别用 |
| 等级 | `t_logout` 的 `curr_lvl` | 只有这个事件有值；量级 1680–4240，**含义存疑** |
| 地块 | `polt_id` | 拼写就是错的 |
| 广告 | `ad_series` / `ad_channel`（用户属性） | `#vp@` 开头的是虚拟属性，数仓不一定有 |
| 首付时间 | **自己用 `row_number()` 算** | `ftime` 在 `t_default` 里释义是"时间(毫秒)"，**不是首付时间** |
| 积分阶段 | `point_stage_before/after` ✅ 有值 | `point_change_cnt` **全空** |

### 归一化固定写法

```sql
CASE
    WHEN os_raw = 'Android'      THEN '安卓'
    WHEN os_raw = 'IPhonePlayer' THEN '苹果'
    ELSE '其他'
END
```

**不要写 `ELSE '苹果'`**——`WindowsEditor` / `OSXPlayer` 这类内部测试机会被静默算进 iOS。同理场景和商品用 `LEFT JOIN` 枚举 + `coalesce` 成 `未知场景_xxx`，匹配不上要能看见。

### 重复注册

`t_register` 有账号存在两条记录。**取 os/country 必须先聚合成一账号一行再 JOIN**：

```sql
SELECT "#user_id" AS user_id, min("#event_time") AS reg_time,
       max(os) AS os_raw, max("#country") AS country_raw
FROM ta.v_event_261
WHERE "$part_event" = 't_register' AND "$part_date" >= '...'
GROUP BY 1
```

## 口径决策（已定，别自己改）

| 项 | 决定 |
|---|---|
| 时间轴 | **24 小时桶**：`date_diff('second', reg, evt) / 86400` |
| 留存命名 | **第 N 日 = D(N-1)**：次日=D1、三日=D2、七日=D6、14日=D13 |
| ⚠️ 陷阱 | 留存的"七日"是 D6，LTV7 是 D7，**两个 7 不是同一天** |
| 付费率分母 | 当日活跃（大盘）/ 新增人数（新增质量表） |
| ARPPU 分母 | 当日付费人数 |
| LTV 分母 | 注册人数 |
| 观测期 | 每个 Dn 只统计满 n+1 天的人 |
| 金额精度 | **整数分累加，最后一次转 DECIMAL**；比率一律 `nullif` |
| 样本阈值 | 分子 ≥30 可用 / 10–29 仅看方向 / <10 样本不足 |
| 呈现 | 表头和维度值全中文，排序走隐藏的日期列 |

金额写法：

```sql
CAST(sum(cent) / 100.0 AS DECIMAL(12,2))                        -- 金额
CAST(sum(cent) / 100.0 / nullif(n, 0) AS DECIMAL(10,4))         -- ARPU 用 4 位
CAST(a * 100.0 / nullif(b, 0) AS DECIMAL(6,2))                  -- 比率
```

ARPU 单独用 4 位小数：量级在 $0.1~$0.5，两位会把 $0.267 和 $0.190 压掉。

## 分析纪律

这些是**每一条都错过一次**换来的。写结论前逐条对照：

1. **决定精度的是分子不是分母**——相对标准误 ≈ `1/√分子`。45 人的分段，留存分子 16 可看方向，付费分子 1.3 完全无意义
2. **观测期未满会伪造下降曲线**——持续导量时最新队列永远显示更差。"付费留存在下降"这个判断就是这么错的
3. **"阶段值"这类跨队列汇总不能横向读**——每列参与的队列不同。iOS LTV 出现 3日 $0.63 → 4日 $0.09 就是这么来的，不是真实回落
4. **必须有对照组**——"体力耗尽导致流失"加入 Core 组后立即证伪
5. **相关性 ≠ 因果**——付费面板与流失 p=0.0064，但 231 条全是曝光无人点击
6. **中位数 ÷ 中位数 ≠ 逐人比值的中位数**——金币倍数从 2027 修正到 561
7. **均值受极值主导时看中位**——均价涨、中位不涨 = 少数大单，不是消费升级
8. **字段名 ≠ 业务含义**——`coin_cnt = 0` 解读成"什么都没得到"是臆测
9. **看全部数据点**——"产出崩塌 8.4 倍"是只挑偶数位置造成的

## 已被推翻的结论

写分析时如果推出这些，说明走错了：

| 曾经的判断 | 实际 |
|---|---|
| `user_action = 1` 是曝光 | **1 是点击，2 才是曝光** |
| `trigger_time` 是废字段 | 101=主动点击、0=自动曝光 |
| `ftime` 是首次付费时间 | 是事件时间戳，含义存疑 |
| 四张通行证共用 trade_id | 枚举显示各有独立 ID，待验证 |
| iOS LTV0 $0.4139 | 被 8/25–8/27 沙盒期零值稀释，作废 |
| 付费留存在下降 | 未满期数据造成的假象，实际稳定在 62–72% |
| 第 2-3 天付费场景没曝光 | 曝光覆盖正常，**变的是人均曝光次数翻倍**（内容耗尽） |

最后一条尤其值得记：**先看分母**。四个场景在 D1 的渗透率都是 15–18%，那个天花板是当天活跃人数，不是场景问题。

## 已知的核心结论

分析时可以直接引用（数据截至 2026-09-02）：

- **卡点在阶段 4**：到达率 58.6% → 15.4%，2352 人（43.2%）卡死。**付费几乎全在阶段 5 之后**（256 个付费者里 251 个）
- **内容终点是阶段 43**：5 人全部卡在那里，人均付费 $50.92
- **大 R 最大单笔不超过 $25**：9 个 $50+ 玩家靠 9–18 笔小额堆起来，最短 2.7 小时买完
- **首笔→次笔转化 52.1%** 是全链路唯一低于 60% 的环节，之后各档 60–93%
- **双端留存无差异**（次日 66.7% vs 65.9%），**档内人均也一致**，差距只在安卓几乎没有大 R
- **收入 72% 集中在首日**，两端一致

## 交付习惯

- 一个查询一个文件，文件名 `qNN_描述.sql`
- 表头和维度值中文，`ARPU$` / `ARPPU$` / `LTV$` 保留英文缩写（和现有看板一致）
- 每张表带 `样本提示` 列自动标记分子薄的格子
- 用 `GROUPING SETS` 一次出明细 + 合计，不跑两遍
- 观测期未满的行用 `WHERE observable = 1` 滤掉，不要留空行让人以为是 0

## 回答风格

- 先说数据自洽性检查（占比加起来是不是 100、明细加总等不等于合计），再说结论
- 结论分「确定的」和「待验证的」，不要混
- 发现自己之前的判断错了，直接说错在哪，不要含糊带过
- 样本不足的格子明确说不能解读，不要给个数字让人以为能用
